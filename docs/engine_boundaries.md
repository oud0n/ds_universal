# 共通エンジンと端末の境界

2026-11-06。解析・選択・再生位置・動画同期・保存制御を `src/engine/` に集めた。実際のファイル、画面、機器はホストが持つ。Windows/MacのElectron、ブラウザ、現行モバイルのWebViewは既存の `src/services/` の入口を通して同じ実装を使う。

## 正本と呼出し

| データ | 一つの実行単位で持つ担当 | 呼ぶ側 |
|---|---|---|
| 点列・周・Car、走行全体の再生秒、再生中か・速度 | EngineSession。Reactはそのsnapshotを購読。周の秒・距離は計算値 | Appが操作を渡し、各画面へ同じsnapshotから値を渡す |
| 選択要求の世代、読込み中の共有要求、走行IDと保存行の対応 | EngineSession.operations。操作自体の組立てはApp | 選択窓口・読込み・古い要求の採否 |
| 保存先の世代・選択中か・読込み期間 | StorageContext | Repositoryのラッパー、コース・定義・走行の読込み |
| 開いている走行と比較走行、未保存項目、保存待ち・動画所有 | RunController | 読込み・同期編集・閉じる操作・保存先切替え前の厳格保存 |
| 動画一覧・照合・時計・プロジェクトの保存形式 | VideoSyncManager | 動画操作・保存担当・再生controller |
| 同期ピンとUTCの基準 | SyncPinStore | 動画操作・RunController。WebではvideoViewStoreが同じストアへ委譲 |
| CSV形式・計算式の準備済み状態 | CsvFormatStore | ログ解析・センサー適用・設定画面 |
| 計算チャンネル・ログ間比較のキャッシュ・測位の選択 | 各factoryのインスタンス | 解析・動画表示・ホストの計測担当 |
| 元ファイル・設定の実保存、動画の再生ハンドル | ホストのRepository/Preferences/Media実装 | コアは窓口を呼ぶ。実際の保存先・URL・デコード方法を決めない |

`createEngineRuntime(ports)` は上記を一組ずつ作る共通の構成入口。既存Webの互換入口は各モデルを一つずつ組み合わせて使い、Appは既存のStorageContextと保存担当を使うEngineSessionを一つ持つ。Webの互換singletonと、新たなruntimeを同じ画面で二重に使わない。別ウインドウ・別端末の同じ物理ファイルへの同時編集を、このインスタンス分離だけで保証しない。

保存先選択は共通のbindStorageLifecycleが厳格保存を待ち、成功した保存先変更で古い担当・動画と要求を解放する。取消では所有を外さない。Runtimeのcloseは進行中の動画準備を失効させ、保存後に確保した資源を解放する。既にホストへ渡した書込み自体の取消しは保証しない。

自動時計補正の要求はEngineSessionがticket、対象と参照の点列、補正の世代、保存先・読込み期間を保持する。Appは見積もりを待った後にその要求が今も有効か確かめ、手動補正や読込み直しより古い結果を適用しない。

解析・動画・走行一覧のページ同士は互いのprivateな状態を参照しない。Appの窓口と共通モデルが受け渡す。各video要素のcurrentTimeは制御対象であり、解析時刻の正本を別に作るものではない。

WebではAppと同じJSコンテキストに正本を一つ置く。比較用Workerは時刻・座標・速度を受け取り、計算結果だけを返す。Electron/端末の窓口は実ファイルや再生資源を持つが、別のCar・解析時計を正本として作らない。将来のネイティブUIも表示用snapshotと入力中の下書きを持ち、確定操作を同じエンジンへ渡す。

## ホストが実装する窓口

- Repository: 一覧・バイト列・厳格な読込み・書込み・ダウンロード・動画資源。実I/O開始後の書込み取消しは保証しない。保存先に結びついたハンドルを使う。
- Preferences: 設定の読書き。Gのならし方とCSV定義は解析側へ明示して渡す。コアはlocalStorageを探索しない。
- Media: バイト列の読込み、メタデータ/GPSの準備、再生ハンドルの作成・解放。File/Blob/URLはWeb側の具体型。
- Scheduler/Clock: 遅延実行・取消し・後続処理・現在時刻。ネイティブ側のキューへ置換可能。
- Course: コースの準備と検索。Viteの同梱、IndexedDB、通信はホスト側。
- PairExecution: ログ間の比較。Web Workerの起動・失敗時の処置はWeb側。コアの比較キャッシュは点列の組に結び付ける。

翻訳は構造化したエラーをWeb入口で表示用に直す。UTF-8、Windows-1252とzlib展開はDOMを使わない実装を使う。

Media.openは呼出しごとに所有する資源のリースを返す。releaseはそのリースだけを受け取り、有効なリースの解放では例外を投げない契約とする。Repositoryのremote.urlは借りた資源であり、このモデルは解放しない。複数資源の準備は公開前に行い、途中失敗では確保分を戻す。設定は最初の物理計算に入力し、後から全点のG計算を繰り返さない。

同期プロジェクトは動画ごとのkeyと元の道を保持し、ピンもkeyで動画に結び付ける。古い形式の名前照合は一意な場合だけ使い、同名で特定できないプロジェクトを別動画へ黙って当てない。空のプレースホルダーでも元フォルダを保ち、別撮影のチャプターを混ぜない。時間比較の各枠は完走時に終点で待ち、完走した枠の音声を時計の元にしない。

ログの復元は元の道・補正前の先頭UTC・part・元ファイルの属性を使う。ブラウザの比較復元にも先頭UTCを持たせる。旧形式は日付・周の開始UTCも照合し、曖昧な候補へ補正やCarを渡さない。計算式・CSV形式は保存先世代と対象ファイルごとのキューで保存と削除を直列化し、要求時の内容を使う。

## 対象外と移植時の残り

今回の境界は解析・同期エンジン。HTMLVideoElement/音声時計・Canvas/WebCodecsの書出し、BLE/GPS/カメラ/IMU、計測中の記録I/O、バックグラウンド動作の組立ては現行ホスト実装として残る。LiveLapTimerの周判定は共通側。timerRuntime自体をネイティブからそのまま呼べるようにしたわけではない。Appのsidecar・コース再計算・読込みUIの組立ても残り、operationsを移しただけで全操作が共通コマンド化されたとは扱わない。

Swift/Kotlin側のホスト、JavaScriptCore等の実行・ブリッジ、メモリ上限、実動画/音声時計、実iCloud、実機の復帰は未検証。ネイティブGUIはまだ作成しない。既存の同期残件がすべて解決したという判定でもない。

## 検査と拡張時の注意

`npm run check:engine` はDOM型なしのコンパイルと、許可したモジュールだけのバンドルを検査する。browser/Node固有のグローバルを使えない別のJS環境で、公開デモの解析→周計算→Car選択→周内の秒→同期の保存/復元を実行する。`npm run build` にも同じ検査を含める。

単体試験では複数runtime、異なる保存先、遅れた応答、保存失敗、取消しを確認する。GUI回帰は別に行う。共通入口が動いても端末実装まで成功したことにはしない。

新しい機能は、(1)保存先/要求の世代、(2)ログIDと元ファイルpart、(3)session秒・lap秒・UTC、(4)動画/保存行の所有者、(5)未保存値の寿命を明示する。別のキャッシュ・ページ内state・ネイティブ側の控えを正本として足さない。独立インスタンス間・アプリ再起動・複数端末の競合は別の試験が必要。

周の控えは再計算失敗をneedsRecomputeで保持し、新しい計測線の結果として旧周を認定しない。非表示の印は道・日付・UTCと一意性を確認して引き継ぐ。動画の撮影判定はGPSを連結する前と再生側で共通にし、同名の別撮影や曖昧なチャプターの時計を混ぜない。

CSVセンサーはGPS点列へ結合した解析用データ、IMUは専用の時刻合わせと融合処理を使っている。計算は共通側にあるが、全データを独立トラックと共通の時間対応表で扱うモデルへ統一済みではない。時間/距離比較は一つの再生位置から求める表示用の対応で、記録機器の時計補正と同一視しない。
