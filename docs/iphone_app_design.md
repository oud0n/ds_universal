# iPhone アプリ版の構想（PLAN-01）

2026-10-19。iPhone・折りたたみの iPhone（以下 Duo。たたむとスマートフォン、開くと小さなタブレットの大きさ、と想定）・iPad で動くアプリの構想。
作り方は 2026-10-19 に決めたとおり、**画面と解析は今の Web をそのまま WKWebView の中で動かし、Swift はネイティブでないとできない部分だけ**にする
（Swift で作り直すと、画面と解析を二重に持つことになるため）。

## 1. アプリでできること

| 機能 | 中身 | 今のブラウザ版との違い |
|---|---|---|
| 解析 | 今の解析・動画・変換の画面すべて | 同じ（ファイルの読み込みと保存だけ、アプリの保存場所を使う） |
| デジスパイスとのつなぎ | 周りのデジスパイスを探し、選んで登録し、次からは自動でつなぐ | 新しい（ブラウザの Safari は Bluetooth を使えない） |
| ラップタイマー | 走っている間、デジスパイスの測位（20 Hz）から周・セクター・基準との差をその場で出す | 新しい |
| カメラ | ラップタイマーと一緒に、iPhone で車載動画を撮る | 新しい |
| 保存 | コース（計測線・セクター・コース図）と走行ログを、アプリの中と iCloud Drive に置く | 新しい（今は毎回ファイルを選ぶ） |

## 2. 作り方（層の分け方）

```
┌───────────────────────────── WKWebView ─────────────────────────────┐
│ 今の Web (React): 解析・動画・変換・コース・ラップタイマーの画面            │
│   ↑↓ ネイティブとのやりとりは 1 つの窓口 (native bridge) だけを通す         │
└──────────────────────────────────────────────────────────────────┘
        ↑↓ WKScriptMessageHandler / evaluateJavaScript (JSON)
┌──────────────────────────── Swift (薄く) ────────────────────────────┐
│ BLE (CoreBluetooth) │ 保存 (FileManager / iCloud) │ カメラ (AVFoundation) │
│ 画面を消さない・バックグラウンド │ 位置 (CoreLocation、デジスパイスがないとき) │
└──────────────────────────────────────────────────────────────────┘
```

- **Web 側の窓口**: `src/native/bridge.ts` を作り、ネイティブの機能はすべてここから呼ぶ。ブラウザ・Electron では今の方法（Web Serial・ファイルの選択）に切り替える。
  画面の部品は「アプリかどうか」で分岐せず、窓口が「できること」（BLE がある・カメラがある・保存場所がある）を返し、それで出し分ける。
- **BLE の受け取り**: Swift は通知のバイト列を、受け取った時刻 (端末の時計ではなく、動画のコマと同じ単調な時計) と一緒に、
  **そのまま走行のファイルに書き足す**（これが記録の元。画面が消えて Web が止まっても、記録は続く）。
  画面が出ている間は、同じバイト列を 100 ms ごとにまとめて Web に渡し、組み立てと解析は今の `digspiceBleProtocol.ts`（feat/ble-protocol）で行う。
  Web が止まっていた間の分は、戻ったときにファイルから読み直す。解析を Swift にも持つと二重になるので、Swift では解析しない。
- **通信の層**: feat/logger-transport の `LoggerTransport`（送受信の層）に、BLE 用の層を足す。USB（Web Serial）と同じ形にそろえる。
  ただし BLE はリアルタイムの測位だけで、設定の変更・ログの吸い出しが BLE でできるかは未解明（TODO の追加キャプチャ）。
- **Web の置き場所**: アプリの中に今のビルド（dist）を入れて、ネットにつながなくても動かす。読み込みは独自の URL の形（`app://`、`WKURLSchemeHandler`）にする。
  **動画のために、範囲の読み出し（`Range` の要求と 206 の応答）を自分で作る**（作らないと、動画の再生・位置の移動ができない）。
  Worker（2 つのログの比べ）がその URL の形で動くか、最初に確かめる（動かなければ、その場で計算する作りがもうある）。
- **Web の保存（localStorage・IndexedDB）は使い捨て扱い**: WKWebView の中の保存は、端末の空きが少ないときなどに消されることがある。
  コース・設定・登録したデジスパイスは、窓口を通して Swift のファイル（`Documents/`・`Application Support/`）に置き、Web の保存は写しとしてだけ使う。
- **作る道具**: Xcode の素の Swift（SwiftUI は外側の枠だけ）。Capacitor などの枠組みは使わない（使う機能が少なく、BLE のプラグインの作りに縛られないため）。
  あとで Android を作るときに Capacitor にするかは、そのときに決める。

## 3. 画面の配置（端末ごと）

今の Web の配置の決め方（画面の幅が 600px より狭ければスマートフォン向け）を、幅の 3 段階にする。端末の名前では決めない（Duo は開くと幅が変わるため）。

| 幅 | 配置 | 当てはまる端末 |
|---|---|---|
| 600px 未満 | スマートフォン向け（今のもの。下のタブ、1 画面ずつ） | iPhone、Duo をたたんだとき、iPad の Split View の狭い側 |
| 600〜1024px | **中くらい（新しい）**: 2 画面を並べる。グラフ解析は速度とコース図を左右、動画は 2 枠を左右、ラップタイマーは大きな数字とコース図 | Duo を開いたとき、iPad mini の縦、iPad の Split View |
| 1024px 以上 | パソコン向け（今のもの） | iPad の横、iPad Pro |

- **Duo を開いた・たたんだ**: 幅が変わったら、その場で配置を切り替える。再生の位置・選んでいる周・撮影は変えない（動画・カメラの部品を作り直さない）。
  **今の「スマートフォンか」の判定（`isPhone`）は、読み込んだときの画面の大きさで決まったまま変わらない**ので、開いても配置が変わらない。
  端末の判定はやめて、幅だけで決める（横向きのスマートフォンをスマートフォン向けのままにするには、高さも見る）。
  折り目の位置を取る方法は、実機と Apple の資料が出てから決める（今は考えない）。
- **横向きのスマートフォン**: 今の横向きの配置（グラフとコース図を左右）のまま。ラップタイマーは横向きを主にする（ホルダーに付けるため）。
- **iPad**: パソコン向けのまま。ロガーとの USB の通信はないので、ロガー設定のタブは BLE のつなぎの画面にする。

## 5. ラップタイマー

走っている間に使う画面。大きな数字で、手で操作しなくてよいようにする。

- **入力（GPS の出どころを選ぶ）**: RaceChrono と同じく、測位の出どころを設定で選ぶ（2026-10-19 決定）。
  - iPhone の GPS（1 Hz 前後。確度が低いことを画面に出す）
  - デジスパイス（BLE、20 Hz）
  - その他の外付けの機器（PLAN-10 の候補: RaceBox、RaceChrono の DIY の BLE、NMEA を送る Bluetooth の GPS、OBD-II（ELM327）など）。
    機器ごとの受け取りは送受信の層（`LoggerTransport`）とプロトコルの層を足す形にし、ラップタイマー・記録は出どころによらず同じにする
  - 選んだ出どころの状態（つながっているか・何 Hz か・測位できているか）を画面の上にいつも出す
- **コース**: 走り始めの位置で内蔵のコース・保存したコースを自動で選ぶ。ないときは、走りながら計測線を自動で置く（PLAN-12 の作り方を、測位が貯まるごとに試す）。
- **出すもの**: 今の周の経過・基準の周（既定はベスト）との差・セクターごとの差（赤・緑。docs/overlay_parts_design.md の 9 と同じ見せ方）・速度。
  周を終えたら、その周のタイムと差を数秒大きく出す。
- **記録**: 測位をそのまま走行ログとして保存する（今の生ログと同じ点の形。CSV・NMEA などへの書き出しは今の変換を使う）。
  あとで解析の画面で開くと、ほかのログと同じに扱える。
- **画面を消さない**: 走っている間は画面を消さない（`isIdleTimerDisabled`）。画面が消えたり別のアプリにしたりすると、WKWebView は数秒で止まる。
  そのため記録は Swift がファイルに書き足して続け（2 の BLE の受け取り）、Bluetooth のバックグラウンドの設定（`bluetooth-central`、つなぎ直しのための
  状態の復元）を入れる。画面が消えている間は、周の表示も声も出さない（戻ったときにファイルから計算し直す）。画面を消したときに知らせる必要はない（2026-10-19 決定）。
- **声で知らせる**: 走りながら画面は見づらいので、周を終えたら周のタイムと差を声で知らせる（`AVSpeechSynthesizer`。Swift の窓口で、画面が出ている間だけ）。
  画面が消えている間は知らせない（周の区切りを Swift でも判定することになり、二重になる。2026-10-19 決定）。
- **熱と電池**: 直射日光の下での画面の明るさ・熱・電池の減りに気をつける。カメラと一緒のときはとくに（6 を参照）。

## 6. カメラ

ラップタイマーと一緒に、iPhone で車載動画を撮る。

- **撮り方**: AVFoundation で撮る。撮っている間は、カメラの映像をラップタイマーの後ろに透けて重ねない（WKWebView を透かして重ねると、
  毎コマ重ね合わせが要り、熱くなる）。ホルダーに付けて撮るので、映像の確認は小さな窓か、撮り始めだけにする。
  既定は 1080p・30 fps・HEVC（60 fps・4K は熱と容量のため、選んだときだけ）。
- **前と後ろを同時に撮る**（2026-10-25）: 対応する端末（`AVCaptureMultiCamSession.isMultiCamSupported`）では、後ろのカメラと一緒に前のカメラ（自分側）も撮れる。
  録画はカメラごとに `AVCaptureMovieFileOutput` を 1 つずつ持ち、つなぎ（カメラ → 録画・映像の枠）は自分で作る。画質は両方とも同時に撮れる形式
  （`isMultiCamSupported` の形式。多くは 1080p まで）から選び、ISO はカメラごとに決める。重すぎる組み合わせ（`hardwareCost` が 1 を超える）は撮らずに知らせる。
  前の動画は `<走行>_front.mov` で、走行の行には `camera: 'front'` を付けて書く。音は後ろの動画にだけ入れる。
- **明るさとピント**（2026-10-25）: ISO を決める代わりに、露出は自動のまま明るさの補正（EV、−2〜+1）だけを選ぶ（車内に合って窓の外が白く飛ぶので、マイナスで外を残す）。
  ピントは遠く（iPhone はレンズの位置 1.0、Android は距離 0 = 無限遠）に合わせて固定する（車内の物にピントが移らないように。固定できないレンズは自動のまま遠くの範囲で合わせる）。
- **時刻**: 端末の時計（`Date()`）は使わない。カメラのコマには、端末の単調な時計での時刻（`CMSampleBuffer` の表示時刻）が付いている。
  BLE の測位を受け取った時刻も同じ時計で記録してあるので、「単調な時計 → GPS の時刻 (UTC)」の対応を測位ごとに作り、それでコマの時刻を GPS の時刻にする
  （BLE の届くまでの遅れは毎回ばらつくので、引く量を決め打ちにしない。「受け取った時刻 − GPS の時刻」がいちばん小さいもの、つまり遅れの少なかった測位を
  下からなぞる直線で対応を作る。ずれの速さ（時計の進みの違い）も同じ直線で出る）。動画のファイルに時刻の情報（QuickTime の時刻つきのメタデータ）として書き込み、
  動画の時刻を「GPS」の種類（docs/video_sets_design.md の 2）として持つ（撮影日時の ±1 秒にならない）。
- **保存**: 撮った動画は、その走行のログと同じ所に置き、アプリの中で走行（ログと動画の組）として扱う。写真のライブラリへの書き出しは選んだときだけ。
- **再生の制限**: 再生は WKWebView（Safari と同じ）なので、2026-10-19 に直した Safari の制限（音のある動画の速さ・止めたままのコマ）がそのまま当てはまる。
  同時に読める動画の数にも上限があるので、スマートフォンでは同時に出す動画を 2 本までにする（今のスマートフォンの配置と同じ）。
- **熱**: 撮りながら BLE・画面・GPS を使うと熱くなる。熱くなったら（`ProcessInfo.thermalState`）画面を暗くし、それでも上がるなら撮るのを止めてログだけ続ける。
- **画面が消えたら撮れない**: iPhone も Android も、アプリが裏に回る（画面を消す）とカメラは止まる。撮っている間は画面を消さないようにし（`system.keepAwake`）、
  それでも消えたら動画はそこで区切り、ログの記録だけ続ける。画面に戻ったら、撮り直すかを聞く（動画は 2 本になり、同じ走行にまとまる）。

## 7. 保存（アプリの中と iCloud Drive）

| 置くもの | 場所 | 中身 |
|---|---|---|
| コース | `Tracks/` | 今のコースのファイルの形（.cln・.sci・.pth）。利用者が置いたもの・編集したもの |
| 走行ログ | `Logs/年-月-日/` | 生ログ（.bon4 など）・アプリで記録したログ・動画・同期プロジェクト |
| 設定 | アプリの中だけ | 登録したデジスパイス・画面の設定（今の localStorage） |

- **アプリの中と iCloud Drive**: 既定はアプリの中（`Documents/`。「ファイル」アプリからも見える: `UIFileSharingEnabled`・`LSSupportsOpeningDocumentsInPlace`）。
  設定で iCloud Drive のアプリのフォルダにすると、コースと走行ログをほかの iPhone・iPad・Mac と共有できる。
  **動画は iCloud に置かない**（30 分で数 GB になり、無料の 5 GB をすぐ使い切る）。動画はアプリの中だけで、端末のバックアップからも外す。
- **今の保存との関係**: Safari（ブラウザ版）の保存は、アプリからは読めない。ブラウザ版で置いたコースは、ブラウザ版から書き出してアプリで開いてもらう
  （ブラウザ版に「コースをまとめて書き出す」を足す）。
- **ファイルを開く**: 「ファイル」アプリの共有・ほかのアプリの「このアプリで開く」で、ログ・動画・コースを受け取れるようにする。

## 7.5 ほかの機器とスマートフォンのセンサー

### つなぐ機器の作り（出どころを足していける形）

位置の出どころ（5 の GPS の出どころ）とは別に、**値の出どころ**をいくつでも同時につなげる形にする。
走行の記録は「出どころごとの値の列（それぞれ受け取った時刻つき）」をまとめたものとし、解析のときに時刻で並べて合わせる。

| 出どころ | つなぎ方 | 取れるもの | 状態 |
|---|---|---|---|
| デジスパイス | BLE | 位置・速度・高度・GPS の時刻（20 Hz） | 解析済み（feat/ble-protocol） |
| iPhone の GPS | CoreLocation | 位置・速度・方位（1 Hz 前後） | 作るだけ |
| iPhone の動きのセンサー | CoreMotion | 加速度・回転（100 Hz まで）。下の「G」 | 作るだけ |
| AiM（Solo 2 DL など） | ロガーの Wi-Fi | 走ったあとのログの吸い出し（WISH-01） | 実機待ち（通信の形を調べる要あり）。.xrk / .xrz の読み込みはできている |
| RaceBox・NMEA の Bluetooth の GPS・RaceChrono の DIY | BLE | 位置・速度（10〜25 Hz）など | 仕様が公開されているものから（PLAN-10） |
| OBD-II（ELM327 など） | BLE または Wi-Fi | 回転数・アクセル・車速・水温など | やるかは未定。問い合わせ式なので、1 つの値あたり数 Hz しか取れない |

- **作りの決まり**: 機器ごとに「送受信の層」（BLE・Wi-Fi・USB）と「プロトコルの層」（バイト列 → 値）を足すだけにし、ラップタイマー・記録・解析は出どころによらず同じにする。
  送受信の層は Swift（BLE・Wi-Fi のソケット）、プロトコルの層は TypeScript（今のデジスパイスの BLE の解析と同じ）。
- **Wi-Fi の機器**（AiM・Wi-Fi の OBD）: 機器の Wi-Fi につなぐと、その間はインターネットに出られない。ローカルネットワークを使う許可（`NSLocalNetworkUsageDescription`）が要る。
  AiM の吸い出しはデスクトップ版（Electron）とこのアプリだけに入れる（ブラウザ版からはソケットを開けないため。2026-10-18 決定）。
- **記録の形**: 記録するのは出どころごとの値の列（`{出どころ, 受け取った時刻, 中身}` を書き足すだけ）で、点の形（`TelemetryPoint`）は解析のときに作る。
  - 点の時刻: 位置の測位が 10 Hz 以上（デジスパイス・RaceBox）なら測位ごと。iPhone の GPS（1 Hz）のように粗いときは、10 Hz の格子で点を作り、間をセンサーでつなぐ（下の 3）。
  - 回転数・アクセルなどは、点の時刻に合わせて補間して入れる（iRacing の .ibt を読むときと同じ: `throttle`・`brake`・`rpm`・`gear`）。
    OBD のように遅い値は、補間でなく直前の値を使う（届いていない間に値を作らない）。
  - センサーの 100 Hz の値は、点にまとめる前に Web で低い周波数だけ残す（下の「振動」）。元の値の列はファイルに残すので、作り方を変えても点は作り直せる。
  - GPS が切れた間（トンネル・ピット）は、点を作らないか、位置のない点にする。どちらにするかは、作るときに今の解析が位置のない点に耐えられるかで決める。

### G（スマートフォンの動きのセンサー）

今の G は、位置と速度の変化から計算している（デジスパイスにはセンサーがないため）。GPS から求める G は、測位の細かさに左右され、少し遅れて、ぶれる。
iPhone の動きのセンサー（CoreMotion: 重力の向き・加速度・回転、100 Hz まで）を使うと、次のことができる。

1. **G を直接測る**: 前後・左右の G を、センサーから直接出す。ただし、ホルダーに付けた向きが車ごとにばらばらなので、**付けた向きの補正**が要る。
   - 下の向き: CoreMotion（Android は SensorManager）が出す重力の向きを使う（センサーの組み合わせで、走っている間もずっと出る。止まっているときだけに頼ると、坂や傾いた場所で狂う）。
     長い旋回の間にこの重力の向きがどのくらい引っぱられるかは、実車で確かめる（UNVERIFIED）。
   - 前の向き: 下の向きに直交する面の中で、角度 1 つを決めればよい。センサーの水平の加速度と GPS の前後 G を、たくさんの時刻で比べて
     いちばん合う角度を選ぶ（最小二乗。速度 20 km/h 以上の間だけ使う）。1 回の加速を待つのでなく、走りながらずっと積み上げて決める。
     ブレーキで車が前に沈むと見かけの向きが数度ずれるが、加速と減速の両方で積み上げると打ち消し合う。
   - 付けた向きが走っている途中で変わったら（ホルダーがずれた）、GPS から求めた G との食い違いで気づいて、決め直す。
2. **GPS から求めた G を補う**: センサーの G（細かく速いが、少しずつずれる）と GPS の G（ずれないが粗く遅い）を合わせて（相補フィルター）、
   遅れとぶれの少ない G にする。フリクションサークルとブレーキの解析が見やすくなる。
   - GPS の速度は、受信機の中の計算で 0.1〜0.2 秒ほど遅れて出る。合わせる前に、センサーの前後 G と GPS の前後 G がいちばん重なるずらし量を求め、その分ずらす。
   - 相補フィルターで足りなければ、あとでカルマンフィルター（センサーのずれの量も一緒に推し量る）に替える。最初からは入れない。
   - **振動**: ホルダーは 15〜40 Hz くらいで揺れ、エンジンの振動はもっと高い。記録は 100 Hz の生のまま残し、G にするときに Web で 5〜10 Hz より上を落とす
     （ネイティブで解析しない決まりのため）。100 Hz より速い振動は記録の時点で折り返して混ざるので、ソフトでは消せない。ホルダーをしっかり付けるよう画面で案内する。
3. **iPhone の GPS だけのときの位置を補う**: 1 Hz の測位の間を、センサーの加速度と回転でつなぐ（位置が 1 秒ごとにしか分からないのを、なめらかにする）。
   ラップの区切りの確かさも上がる。
4. **回転の速さ（ヨーレート）**: 回転のセンサーで、向きの変わる速さを直接測れる。今は位置から求めている旋回半径の確かさが上がる。

- **記録**: センサーの値はラップタイマーで走っている間、出どころの 1 つとして記録する（100 Hz のまま。位置の点には、合わせた G を入れる）。
- **デジスパイスとの組み合わせ**: 位置はデジスパイス（20 Hz）、G は iPhone のセンサー、のように出どころを組み合わせられる。
  デジスパイスのログを、あとで iPhone のセンサーの記録と時刻で合わせることもできる（2 つのログの比べと同じ考え）。
- **確かめること**: 車の振動でセンサーがどのくらいぶれるか（ホルダーの固さによる）、付けた向きの自動の補正がどのくらいで決まるか。実車で記録して確かめる。

## 7.6 ネイティブとの約束（窓口の仕様）と Android への移植

Android のアプリも同じ Web を使えるよう、Web とネイティブの間の約束を先に決め、iPhone（Swift）と Android（Kotlin）はその約束を作るだけにする。
**ネイティブ側には、解析・周の判定・機器ごとのデータの読み方を入れない**（入れたものは両方で書くことになるため）。
例外は、Android の擬似ロケーションのための標準の形の読み方だけ（下の「Android だけの機能」。読み方の見本で、ずれないようにする）。

### 決まり

- **約束は TypeScript で書く**（`src/native/contract.ts`）。名前・引数・返す値・知らせ（イベント）の形をここで決め、版の番号を付ける。
  ネイティブは起動時に版の番号と「できること」を返す。Web は「できること」で画面を出し分け、端末の種類では分けない。
- **やりとりの形**: JSON の 1 通ごとに `id` を付け、呼び出しには `id` つきの答えが返る（Promise）。ネイティブからの知らせは `event` の名前つき。
  バイト列は base64 にする。20 Hz の通知などは、ネイティブで 100 ms ごとにまとめて 1 通にする。
  センサーの 100 Hz の値は、画面に渡すときは 20 Hz に間引く（記録は 100 Hz のまま）。記録したファイルの読み直しは JSON で送らず、
  `files.mediaUrl` と同じ URL から `fetch` で読む（何 MB にもなる base64 を一度に送らない）。
- **時計**: ネイティブが付ける時刻は、すべて**同じ単調な時計**（ナノ秒）。UTC への対応は、GPS の測位から Web が作る。
  - iPhone は `mach_absolute_time`。カメラのコマ（ホストの時計）・CoreMotion の時刻（`systemUptime`）と同じ時計なので、そのまま並べられる。
    端末が眠っている間は進まないが、すべての出どころが同じ時計なので、並びは崩れない（UTC への対応は測位ごとに作り直すので、眠った前後で別に作る）。
  - Android は `SystemClock.elapsedRealtimeNanos`（センサーの時刻と同じ）。カメラのコマの時刻は機種によって別の時計のことがある
    （`SENSOR_INFO_TIMESTAMP_SOURCE` が `REALTIME` でないとき）。そのときは、コマを受け取った時刻との差を測って直す。
- **エラー**: 決まった符号（`permission-denied`・`not-supported`・`not-connected`・`io`・`busy`）と、利用者に見せる文言（日本語・英語）を返す。
- **許可**: 許可が要る機能（Bluetooth・カメラ・位置・ローカルネットワーク・マイク）は、使う直前に Web から頼み、状態（許可・拒否・未確認）を返す。
  一度断られると、OS はもう聞いてくれないので、拒否のときは `system.openSettings()` で設定の画面に案内する。

### 約束の中身

| まとまり | 呼び出し | 知らせ | iPhone | Android |
|---|---|---|---|---|

- **記録（`recorder`）は出どころをまとめて受け持つ**: 走っている間、`ble`・`location`・`motion` から届いたものを、解析せずに時刻つきでファイルに書き足す。
  画面が出ている間は、同じものを知らせでも Web に渡す。画面に戻ったら、Web は `recorder.url` から抜けた分を読み直す。
- **つなぎ直しもネイティブが受け持つ**: 画面が消えている間は Web が止まっているので、BLE が切れても Web はつなぎ直せない。
  `recorder.start` に渡す出どころの一覧に「どの機器の・どのサービスの・どの特性を読むか」まで書いておき、切れたらネイティブが同じ手順でつなぎ直す。
  これは機器ごとの決まりではなく、一覧に書いた手順をくり返すだけなので、ネイティブに機器ごとの読み方は入らない。
  - `connect` の `決まり` には、つなぎ直すか・送れる大きさ（MTU）・速く送る設定を書く。Android では、つないだあと MTU を上げ、速く送る設定（`CONNECTION_PRIORITY_HIGH`）にしないと 20 Hz が届かないことがある。iPhone では OS が決めるので無視する。
- **ブラウザ版・Electron 版の窓口**: 同じ約束を Web だけで作る（`ble` はなし、`serial` は Web Serial、`files` はファイルの選択と書き出し、`camera` はなし）。
  画面は窓口しか呼ばないので、ブラウザ版とアプリで画面の作りが分かれない。
- **試すための窓口**: ネイティブのふりをする窓口（TypeScript）を作り、記録したバイト列を流す（今の BLE の解析の確かめと同じ）。
  約束の試験をこの窓口で走らせ、iPhone・Android の窓口にも同じ試験をかける。
  ふりをする窓口も、やりとりは必ず JSON の文字列にしてから通す（TypeScript の中で物をそのまま渡すと、`undefined` と `null` の違い・base64 の誤りなどが試験をすり抜けるため）。
  やりとりの見本（JSON のファイル）を約束と一緒に置き、Swift・Kotlin の試験でも同じ見本を読ませる。

### Android への移植で考えておくこと

- **同じものが使える**: Web のすべて（画面・解析・BLE のデータの読み方）。Android の WebView は Chrome と同じ仕組みなので、Safari 向けの直しの多くは要らない。
- **書き直すもの**: 上の表の Kotlin の列。作業の大きさは、iPhone のネイティブの部分と同じくらい（設計は済んでいるので、それより少し小さい）。
- **Android のほうが楽なもの**: 画面を消したあとの記録（常駐の通知を出すフォアグラウンドサービスで続けられる）、USB でのデジスパイスとのつなぎ。
  ただし Android 14 からは、サービスの種類（`connectedDevice`・`location`）を書いて、それぞれの許可を取る必要がある。
- **Android のほうが手間なもの**:
  - 機種ごとの違い（BLE・カメラ・GPS）。確かめる端末を何台か用意するか、試してくれる人が要る。
  - **BLE が不安定**: 切れる（よく出る状態 133 など）ことが iPhone より多い。BLE の操作（つなぐ・探す・読む・書く）は 1 つずつ順に行う決まりにし（同時に出すと失敗する）、
    つなぐときは `autoConnect = false`（true だとつながるまで数十秒かかることがある）。切れたらつなぎ直す（上の「つなぎ直し」）。
  - **電池の節約で止められる**: Xiaomi・Samsung などは、フォアグラウンドサービスでも止めることがある。初めて走るときに、電池の節約の対象から外すよう案内する（`system.batteryOptimization`）。
  - **動画の形式**: WebView で HEVC を再生できるかは機種しだい（UNVERIFIED）。Android で撮るときの既定は H.264 にする。
  - **動画の範囲の読み出し**: `WebViewAssetLoader` は動画の途中から読む頼み（Range）に答えないので、範囲で返す読み出しを Kotlin で書く（iPhone の `app://` と同じ仕事）。
  - **折りたたみ**: 開いたり閉じたりすると、何もしないと画面（Activity）と WebView が作り直され、走っている状態が消える。
    `configChanges` で作り直さないようにし、幅の変化として Web に伝える。
- **配り方（2026-10-19 決定）**: 開発者の登録（1 回 25 USD）をして、早めに Google Play に出し、試してくれる人を募る。
  - 個人の新しい開発者の登録は、一般に公開する前に「クローズドテスト」を、決まった人数以上（12 人と聞いている。登録するときに Play Console で確かめる）が 14 日続けて参加した状態で行う必要がある。
    この期間を、試してくれる人を募る場として使う（みんカラ・X・README で呼びかける）。
  - 機種ごとの違い（BLE・GPS・電池の節約）は、試してくれる人の端末で確かめる。不具合の報告の書き方（機種・Android の版・何をしたか）を、呼びかけと一緒に出す。
- **入れないもの**: ネイティブで解析・周の判定をしない、Safari 向けの直しを「iPhone かどうか」で入れない（「その制限があるか」で入れる）。
  例外は下の「擬似ロケーション」のための、標準の形の読み方だけ。

### Android だけの機能: 擬似ロケーション（ほかのアプリにも位置を渡す、2026-10-19 決定）

デジスパイスなどの GPS ロガーの位置を、Android の位置として流し、地図・RaceChrono など**ほかのアプリも 20 Hz の位置で動く**ようにする。
同じことをする有料のアプリはあるが、このアプリの中の機能として無料で入れる（そのアプリの作りやコードは見ず、Android の公開の仕組みだけで作る）。

- **仕組み**: 使う人が「開発者向けオプション」→「仮の現在地情報アプリを選択」でこのアプリを選ぶ。
  アプリは `LocationManager.addTestProvider`（GPS の提供者の名前で）を作り、1 測位ごとに `setTestProviderLocation` で位置・速度・方位・高度・時刻・精度を渡す。
  選ばれていないときは、その案内（設定の画面を開くボタンと手順）を出す。
- **常駐**: 画面を消しても流し続けるので、フォアグラウンドサービス（種類 `location` と `connectedDevice`）で動かす。止めるのは通知かアプリの画面から。
- **つなぎ**: アプリの中のペアリング（4）と同じ機器の登録・つなぎ直しを使う。デジスパイスは BLE だけ（USB はリアルタイムの位置を送らない）。
- **読み方をネイティブにも持つ（決まりの例外）**: 画面が消えて Web が止まっている間も流し続けるため、バイト列を位置にする処理を Kotlin にも持つ。
  対象は、仕様が公開されている標準の形だけにする: Bluetooth の Location and Speed（デジスパイス）、NMEA（多くの Bluetooth の GPS）、RaceBox の公開の形。
  それ以外の機器・解析・周の判定は、今までどおり Web だけ。
- **読み方を 2 つ持つので、ずれないようにする仕組み**（下の「読み方の見本」）。
- **確かめること**: 受け取る側のアプリが何 Hz で使うか（OS やアプリが間引くことがある）、擬似の位置を断るアプリ、電池の減り。

### 読み方の見本（Web とネイティブで読み方を 2 つ持つときの決まり）

同じバイト列の読み方を TypeScript と Kotlin（必要なら Swift）で持つときは、どちらも**同じ見本のファイル**で試験し、片方だけ直すと試験が落ちるようにする。

- 見本: `src/native/fixtures/<形の名前>.json` に、入力（バイト列の 16 進・NMEA の文）と、期待する結果（時刻・緯度経度・速度・高度・測位できているか）を並べる。
  実機のキャプチャから取った例と、境目の例（未測位・年が 0・A のない B・長さ違い）を入れる。
- TypeScript の試験と Kotlin の試験が、同じ見本を読んで比べる。読み方を直したら、見本も直す（見本を直すと、もう片方の試験が落ちるので気づく）。
- GitHub Actions で両方の試験を走らせる。読み方のファイル（`digspiceBleProtocol.ts` など）を変えた変更で、見本を変えていなければ知らせる。
- 読み方のファイルの頭に、もう片方の場所と見本の場所を書いておく。

## 8. 進め方（案、レビューを受けて並べ直した）

1. **枠と保存**: Swift の枠と WKWebView、`app://` での読み込み（動画の範囲の読み出しを含む）、窓口（bridge）の最初の形。
   コース・設定・ログを Swift のファイルに置き、「ファイル」アプリ・共有から受け取る。今の Web がそのまま動くことを確かめる（TestFlight で配る）
2. **画面の配置**: 端末の判定をやめて幅だけで決める、中くらいの幅（Duo を開いたとき・iPad mini）
3. **BLE**: 探す・登録する・つなぐ・ファイルに書き足す・画面に渡す（feat/ble-protocol と feat/logger-transport をマージしてから）。
   走行中の BLE のログを取り、速度の単位を確かめる
4. **ラップタイマー**: 画面・声で知らせる・画面が消えていた間を戻ったときに計算し直す
5. **カメラ**: 撮る・コマの時刻を GPS の時刻にする・走行にまとめる・熱の見張り
6. **iCloud Drive**（コースと走行ログだけ。動画は置かない）
7. **iPhone のセンサーの G**: 付けた向きの自動の補正・GPS の G との合わせ（ラップタイマーと同じころでもよい）
8. **ほかの機器**: 仕様が公開されている BLE の機器（RaceBox など）→ AiM の吸い出し（実機が届いてから）→ OBD-II（やるなら）
9. **Android 版**: Kotlin の窓口（約束は同じ）→ 擬似ロケーション（読み方の見本と一緒に）→ Google Play のクローズドテストで試してくれる人を募る → 公開。
   最初の版は、BLE のつなぎ・リアルタイムの表示・擬似ロケーション・今の解析の画面まででよい（ラップタイマー・カメラは iPhone で作ったあとに）
