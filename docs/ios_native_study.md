# iPhone のアプリをネイティブにするかの検討（PLAN-20）

2026-10-23。動画の「比べる」が iPhone でときどきカクつく件（BUG-32）をきっかけに、iPhone のアプリをネイティブ（Swift）にした場合に、どこまで Web と共有できるかを検討した。
Fable・Opus 5.5（High）・agy（Gemini 3.8 Flash High）の 3 者に、コードを読むだけで 3 回（各自の案 → 互いの案への反論と修正 → 最終案）回してもらい、食い違いはコードで確かめた。

## 結論

- **画面をネイティブで作り直す必要はない。** 1 つの Web アプリを iPhone・パソコン・ブラウザ（あとで Android）で共有したまま、Swift は「画面を持たない、Web ではできないことだけ」を受け持つ今の形を続ける。
- **「動画以外を共有する」最小の形は作れる。しかも、動画全部をネイティブにする必要もない。** 作り方を変える必要があるのは、「比べる」で再生の速さが変わり続ける Car 2〜4 の枠だけ。それも、まず Web のまま（WebCodecs）で試せる。
- **作り直したあとも、ふだんの変更の 9 割ほどは 1 回書けば済む。** 2 回書くのは、ネイティブの窓口に足す機能（新しい通信のつなぎ方・ファイルの操作など）くらい。

画面を SwiftUI で作り直す案（18〜35 人週）と、計算の部分まで Rust などで作り直す案（30〜60 人週）は、3 者とも退けた。画面・グラフ・動画の部品を変えるたびに 2〜3 回書くことになるため。

## 分け方（勧める形）

| 部分 | 置き場所 | 理由 |
|---|---|---|
| 計算（読み込み・周・物理・解析・機器の読み方 `devices/*`） | 共有（TS） | もともとブラウザに頼らない。Swift では解析しない決まり |
| 画面・グラフ | 共有（TS） | SwiftUI に写すと、画面の変更が毎回 2 倍（Android で 3 倍） |
| ラップタイマーの計算と画面 | 共有（TS） | `liveLapTimer.ts`・`timer/*` のまま |
| 画面を消している間の記録 | ネイティブ（画面なし） | 止まった WKWebView は書けない。Swift が測位の元のバイト列を走行のファイルに書き足し、戻ったら Web が周を数え直す |
| メーターなどの部品・書き出し | 共有（TS） | 1 つの描き方で、画面と書き出しが同じになる |
| 動画の再生（見る・マルチカメラ・音） | 共有（TS） | `<video>` と `PlaybackController`。音を出している動画が時計の元 |
| 比べるの Car 2〜4（速さが変わる枠） | 共有（WebCodecs）。だめならネイティブ | ネイティブにするときは `AVAssetReader` → `AVSampleBufferDisplayLayer` を、透明にした WKWebView の下に置く。時計・配置・指の操作・部品は Web のまま |
| 保存の形（runs.json など） | 共有（TS） | Swift はファイルを読み書きするだけ |
| Bluetooth・動き・カメラ | ネイティブ（画面なし） | バイト列をそのまま Web に渡し、読むのは TS |
| Web の置き場所・通信なしでの起動 | ネイティブ（小さな読み込み口） | アプリに Web を入れておけば、電波のないサーキットでも起動でき、走行のフォルダの動画もページから直接読める |

**窓口の決まり**: ネイティブの約束（`src/native/contract.ts`）は、版を上げずに機能を足すだけにする。
配っているアプリは Web を GitHub Pages から読むので、版が合わないと `nativeCapabilities()` が null を返し（`bridge.ts` 108〜118 行）、入っているアプリ全部で Bluetooth やファイルが使えなくなる。

## 作り直したあとのメンテナンス

**2 回書く（TS と Swift、あとで Kotlin）もの**
- ネイティブの窓口に足す機能（新しい通信のつなぎ方、ファイル・端末の操作）
- 画面を消している間に Swift が書き足す記録の決まり
- （ネイティブの動画にした場合だけ）Car 2〜4 の付いていき方。距離の対応の計算そのものは TS のまま（Web が計算した対応表を渡す）

**1 回書いて、iPhone で確かめるだけのもの**

| 変更 | iPhone で確かめること |
|---|---|
| 新しいログの形式 | iCloud のフォルダから 1 本読み込む |
| 周・セクターの直し | 単体テストで足りる |
| 新しい画面・グラフ | スマートフォンの幅・安全領域・回転 |
| 新しいメーターの部品 | 動画の上に正しく出るか（ネイティブの動画なら位置のずれ） |
| 動画の同期・比べるの変更 | 実機で 2 枚の比べる（CDP で記録を取る） |
| 保存の形の変更 | iCloud のフォルダで読み書きを 1 往復 |
| 新しい Bluetooth の機器 | 実機で、画面を消したときも |

1 回で済む変更の割合: WebCodecs でいけば 95〜100%、ネイティブの動画が要れば 90% ほど。

## 進め方

| 段階 | 中身 | 手間 | 次へ進む条件 |
|---|---|---|---|
| P0 | BUG-32 を実機で計測（CDP: 枠ごとのコマ・位置を飛ばした・速さを変えた時刻）。比べるで Car 1（1 枠目だけ）を時計の元にする | 半日〜1 日（Web だけ。Pages で届く） | カクつきが消えれば、動画の作業はここで終わり。Car 2 の速さの変更・飛びと重なれば P2。どちらとも重ならなければ、動画の作りの問題ではない |
| P1a | 画面を消している間の記録を Swift が書き足す（動画の判断とは別） | 1 人週ほど（アプリの更新が要る） | 安い形: 走行のたびに今の `recorder.*` を一緒に動かし、戻ったときにすき間を埋める。iPhone の GPS は裏で動かす設定がないので対象外 |
| P1b | Web をアプリに入れ、独自の URL の形で読む。同じ口で走行のファイルも出す（動画の判断とは別） | 1〜2 人週 | 通信なしで起動でき、ページから動画を直接読める。代わりに、Web の直しが TestFlight / App Store の更新を通らないと届かなくなる |
| P2 | 比べるの Car 2〜4 を WebCodecs で描く。まず 1〜2 日の試作 | 2〜4 人週 | 合格: FHD 60p（H.264・HEVC）を、Car 1 が音を出している間に実時間の 1.5 倍以上で解け、約 1 秒先まで読んでおいて飛びを隠せ、メモリが増え続けない |
| P3 | P2 がだめなときだけ: Car 2〜4 をネイティブで描く（iPhone だけ）。まず 2 日の試作 | 3〜5 人週 | 速さを変えても滑らかか、透明な WKWebView の下で位置がずれないか |

- Android は WebView（Chromium）のまま。先に Android の実機で 2 枚の比べるを試し、カクつくときだけネイティブの再生（Media3）を考える。
- P1b で「通信があるときは Pages、ないときはアプリの中」と混ぜる場合、ブラウザの保存（localStorage など）は読み込み元ごとに分かれる。設定を先に Swift のファイルへ移しておく。

## P0 の結果（2026-10-23、iPhone の実機で CDP 計測）

サンプルの FHD の動画 2 本 (8/15 と 9/18 の袖ヶ浦) の比べるで、コマが出た時刻・位置を飛ばした時刻・速さを変えた時刻を記録した。

| | 直す前 (Car 1 を時計の元にしただけ) | 速さの変更も抑えたあと |
|---|---|---|
| Car 1 のコマの止まり | 0 | 0 |
| Car 2 の速さの変更 | 977 回 / 約 80 秒 | 61 回 / 約 85 秒 |
| Car 2 のコマの止まり (0.1 秒超) | 40 回以上 | 3 回 |

- Car 2 は、距離の対応の傾き (元の速さ) が 0.995〜1.005 と揺れ続け、そのたびに「詰め終えたら元の速さへすぐ戻す」が効いて、1 秒に 12 回ほど速さを変えていた。
- 残った 3 回は、どれも速さを変えた直後に止まり、遅れて位置を飛ばす形。WebKit で速さを変える限り残るので、消すなら P2 (WebCodecs)。

## 検討でわかったこと

- **比べるでは Car 1 も飛んでいる。** 比べるのときだけ、音を出している動画を時計の元にしていない（`VideoSyncWindow.tsx` 625〜626 行）。iPhone では音のある動画の速さを変えないので、Car 1 は 0.2 秒遅れるたびに位置を飛ばし、そのたびに 0.4〜0.6 秒止まる。BUG-32 の原因の候補で、直すなら 10 行ほど。
- **ネイティブにしても、`AVPlayer`・`AVPlayerItemVideoOutput` では直らない。** どちらも、欲しい時刻のコマを出すには速さを変えるか位置を飛ばす必要があり、同じ引っかかりが残る。避けられそうなのは `AVAssetReader` で順に解いて `AVSampleBufferDisplayLayer` の時計の速さだけを変える形（未確認）。
- **画面を消している間は、ラップタイマーの走行が記録されない。** 走行のファイルは Web が `system.appendFile` で書いていて（`runRecorder.ts` 142〜180 行）、裏に回ると Swift は測位を Web に送らない（`BleModule.swift` の enqueue）。Swift が書き続ける `BleRecorder` は、キャプチャの画面でしか使っていない。
- **今のアプリは、電波がないと起動できないと思われる（未確認）。** 起動のたびに GitHub Pages から入口のページを取り直し、オフライン用の仕組みがない。
- **ページから `lapfile://` の動画を `fetch` では読めない。** `<video>` には出せるが、バイト列は窓口の `system.readRunRange`（base64、1 回 8 MB まで）でしか読めない。WebCodecs に回すとき、この速さが足りるかは測る必要がある（P1b で同じ読み込み元にすれば要らなくなる）。

## 残っている食い違いと、決め方

| 食い違い | 決め方 |
|---|---|
| ネイティブの動画にしたとき、時計を誰が持つか（agy: ネイティブ、Fable・Opus: 音を出す Car 1 を持つ Web） | P3 の試作で、時刻を焼き込んだ動画 2 本を画面録画し、Web の時計に合わせたネイティブの枠が 1 コマ以内に収まるか |
| 窓口（base64）で動画のバイト列が足りるか（agy: 無理、Fable・Opus: 足りるかもしれない） | 走行中に GoPro の 60 秒分を 1〜8 MB ずつ読み、MB/秒と、ページの処理の止まり（50 ms 超）を測る |
| 飛んだあとに許す遅れ（agy: 50〜100 ms、Fable・Opus: 1 秒先読みで 150 ms） | 実際の GoPro の動画のキーフレームの間隔と、そこから目的のコマまで解く時間を測る |
| Android にネイティブの動画が要るか | Android の実機で 2 枚の比べる |
